# Separate Nexora and Loopza case registration numbers

The group and product case registries use independent database-backed counters.

| System | Prefix | Example |
|---|---|---|
| Nexora Group general cases | NEX | NEX-2026-000001 |
| Loopza Trace & Find cases | LTF | LTF-2026-000001 |

Rules:

- Each system has its own yearly sequence. Incrementing one does not consume numbers from the other.
- Sequence allocation is performed in a database transaction and locks the system/year row before incrementing.
- The unique system/year constraint prevents duplicate counter rows.
- The case table's unique `case_reference` constraint remains the final duplicate safeguard.
- References are generated by `App\\Services\\CaseReferenceNumber`. Only the explicit `nexora` and `loopza` scopes are accepted.
- Existing Loopza records keep their original references. New Loopza cases use the sequential LTF format.
- Nexora's general-case creation workflow should call `app(CaseReferenceNumber::class)->next('nexora')` when its case record is persisted. This PR provides the independent counter; it does not invent a general-case model or route that is not yet present.

Production note: MySQL/InnoDB is the intended concurrent production database. Keep the unique index and transaction/row lock; do not allocate references in the browser or from an in-memory counter.
